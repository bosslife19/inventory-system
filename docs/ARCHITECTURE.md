# System Architecture

## Actors & hierarchy

```
Federal (national)
  └── State (36 states + FCT)
        └── LGA (774 nationally)
              └── Facility / SDP (Service Delivery Point)
```

Every user account is anchored at exactly one level (`facility_id`,
`lga_id`, `state_id`, or `federal` role with no id). A user can see their
own node plus everything beneath it — never above or sideways.

## Core modules

| Module | Description |
|---|---|
| Product catalog | Master list of trackable products, unit of measure, stock thresholds |
| Stock Card (transactions) | Receipts, issues, losses/adjustments, physical counts — append-only ledger, one row per Excel "Stock Card" row |
| Stock balances | Materialized current on-hand quantity per facility+product(+batch) |
| Delivery notes | Incoming shipment capture, mobile-scanned or manually entered, becomes receipt transactions after review |
| Alerts & notifications | Low stock, expiring soon, expired, stock-out — generated by scheduled jobs, delivered via push (mobile), and in-app (web) |
| Reporting / rollups | LGA/State/Federal aggregate views computed from facility-level balances |
| Admin | Manage hierarchy (states/LGAs/facilities), users, roles, product catalog |

## Data flow

1. SDP staff records a transaction (web or mobile) → `stock_transactions`
   row is inserted → `stock_balances` for that facility+product+batch is
   updated **synchronously, in the same request** (an O(1) delta apply,
   not a re-sum of history — see "Balance recalculation" below) → alert
   rules re-evaluate that row.
2. Delivery note scanned on mobile → uploaded image + OCR/barcode result →
   backend creates a **draft** delivery note with line items → SDP staff
   confirms on web or mobile → confirmation creates the actual receipt
   transactions (never auto-post without human confirmation — matches the
   real-world control of signing for a delivery).
3. A cron-triggered scheduled task (not a queue worker — see "Hosting
   constraints") computes Average Monthly Consumption (AMC) per
   facility+product from the last N months of issue transactions, and a
   suggested reorder quantity, mirroring the "Bin Card" summary sheet in
   the Excel template (Min SL / Max SL / AMC / Quantity to Order). The
   same scheduled task does a full reconciliation pass — resumming
   `stock_transactions` from scratch and comparing against the live
   `stock_balances` value — as a safety net against drift, since nothing
   else touches that table.
4. State/Federal dashboards read from `facility_product_status`, a
   materialized status row per facility + product (refreshed inline after
   each ledger write and by a daily scheduled pass), rather than summing
   raw balances live, so rollups stay fast at scale. The LGA rollup is
   small enough to compute live. Dashboards poll
   (React Query `refetchInterval`, e.g. every 30–60s) rather than
   receiving a live push, since there's no persistent WebSocket server
   on shared hosting.

## Balance recalculation — how it actually works

`stock_balances` is never written to directly and never queued as a
separate async step. `StockLedgerService::record()` does the whole thing
inline, inside one DB transaction, per write:

1. Lock the facility row (`SELECT … FOR UPDATE`), serializing ledger
   writes per facility so balances and the date-order check can't race.
   Writes to different facilities don't contend.
2. Resolve the batch by `(product_id, batch_no)`; inbound types and
   `physical_count` may create a new batch (with `expiry_date`), outbound
   types must reference an existing one.
3. Look up (or create) the `stock_balances` row for this
   facility+product+batch and compute the new value for the transaction
   type — `quantity` is always positive, direction comes from the type
   (`App\Enums\TransactionType::apply()`):
   - add: `receipt`, `transfer_in`, `adjustment_in`
   - subtract: `issue`, `loss`, `transfer_out`, `adjustment_out`
     (rejected if it would take the batch below zero)
   - replace: `physical_count` sets the batch balance to the counted total
4. Insert the `stock_transactions` row with `running_balance` = the new
   **facility+product** total (this batch's new value + the product's
   other batch rows at the facility) — matching the STOCK BALANCE column
   of the paper Stock Card, which is per product, not per batch.
5. Update `stock_balances.quantity_on_hand` for the batch.

Also enforced here (so every caller, including delivery-note
confirmation, obeys them): no future `transaction_date`; no entry dated
before the product's latest entry at that facility (the card is written
in date order and `running_balance` is an insert-time snapshot); expired
batches can't be `issue`d, only written off (`loss` etc.).

This is a few indexed lookups + insert + update — it doesn't matter how
long a facility's history is, so there's no need for a background job or
a queue to keep it fast. A **separate, periodic** full reconciliation
(`php artisan stock:reconcile`, scheduled hourly 00:00–05:00 WAT) re-sums
the whole ledger and corrects any drift in `stock_balances`; that's the
only place the ledger is ever fully re-scanned. It works facility by
facility within a time budget (`--max-seconds`, default 50) and resumes
on the next run, so it fits shared-hosting execution limits; once a full
pass completes it idles until the next day. Historic `running_balance`
mismatches are logged, never rewritten.

## Hosting constraints (shared/cPanel hosting)

Shared hosting typically gives you PHP-FPM, MySQL, and cron — not Redis,
not a process manager for daemons, not WebSockets, and often a short PHP
execution timeout (30–60s). Design choices that follow from this:

- **No queue worker.** `QUEUE_CONNECTION=sync` (or `database` if you want
  a durable fallback queue without a worker daemon) — `ShouldQueue` jobs
  run inline. The balance-recalc path is synchronous by design anyway
  (see above), so this mainly affects things like sending push
  notifications, which are cheap enough to run inline too.
- **No Redis.** Cache, session, and queue drivers all use `database` or
  `file`.
- **Scheduled tasks via cron, not `queue:work`.** One cron entry running
  `php artisan schedule:run` every minute drives everything periodic
  (AMC calculation, reconciliation, alert detection) — this is the
  standard shared-hosting-compatible pattern for Laravel's scheduler.
- **No Laravel Reverb / WebSockets.** Dashboards poll instead. Revisit
  only if/when this moves to a VPS.
- **Keep the request-time path cheap.** Since balance updates now happen
  inline instead of being offloaded to a worker, avoid adding anything
  slow to `StockLedgerService::record()` — it needs to comfortably clear
  in well under the host's PHP timeout even under load.

## Tech stack

- **Backend**: Laravel (API-only), MySQL (shared-hosting compatible —
  most cPanel-style hosts don't offer PostgreSQL), Laravel Sanctum for
  auth, Firebase Admin SDK for push notifications.
- **Deployment target: shared/cPanel-style hosting, not a VPS.** This
  rules out a few things a "default" Laravel setup assumes — see
  "Hosting constraints" below. If you later move to a VPS, the
  constraints in that section can be relaxed one at a time (real queue
  worker, Redis, Reverb) without a rewrite, since the code is written
  against the constrained baseline first.
- **Web**: React (Vite), TypeScript, React Query for server state, a
  charting library (Recharts) for rollup dashboards, role-aware routing.
- **Mobile**: React Native (Expo recommended for camera/barcode/push APIs
  out of the box), offline queue (WatermelonDB or a simple local SQLite +
  sync table), Firebase Cloud Messaging for push.
- **Contract layer**: OpenAPI spec generated from Laravel (e.g. via
  `dedoc/scramble` or hand-maintained in `docs/API_CONTRACT.md`), then a
  generated TypeScript client in `shared/types/` consumed by both web and
  mobile so field names never drift between the three apps.

## Why this shape

The Excel template you supplied is effectively the row-level schema for
`stock_transactions` (Date, Voucher No, Received From/Issued To, Batch No,
Expiry Date, Qty Received, Qty Issued, Losses/Adjustment, running Stock
Balance) plus a summary "Bin Card" sheet (Min/Max Stock Level, Emergency
Order Point, AMC, Quantity to Order). The system digitizes that exact
model per facility, then adds the rollups and alerting a paper form can't
do on its own.
